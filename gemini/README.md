# VORTEX-GEN 3.0 "Centaur"

VORTEX is a local-first and cluster-capable agentic workflow engine for generative AI. It uses a Rust control plane, Python inference workers, and a vertical rack UI that compiles to a DAG for execution. The system targets zero-copy data transport, strong governance, and repeatable, auditable runs.

Status: SRS complete, implementation in progress.
License: Apache 2.0.

## Why VORTEX

VORTEX is an MCP-style tool box for humans and AI agents. It turns natural language intent into reusable workflow templates, enforces human-in-the-loop (HITL) approvals for sensitive actions, and records run artifacts with full audit trails.

Key outcomes:
- Templates are first-class artifacts with versioning and parameter schemas.
- Runs are auditable and reproducible with full lineage.
- Policies and authorization are server-enforced, not UI-only.
- GPU inference can run locally or on remote GPU workers.

## Core Concepts

- **Rack**: Vertical list of units in the UI (no infinite canvas).
- **Signal Bus**: Lane-based routing between units.
- **Template**: Versioned workflow graph generated by AI or humans.
- **Run**: A single execution of a template with parameters.
- **Artifact**: Persisted output from a run (image, tensor, metadata).
- **Approval Gate**: A mandatory human approval step in a workflow.

## Architecture Overview

```
UI (Svelte 5)  <->  Core Engine (Rust)  <->  Worker Fabric (Python)
   |                      |                        |
   | HTTP/WS              | Protobuf + UDS/TLS      | PyTorch + Arrow
   v                      v                        v
Vertical Rack         Graph Compiler           GPU/CPU Execution
                      + Scheduler              + SHM (local to worker)
```

Deployment modes:
- **Local**: Core and Worker on the same machine (UDS + SHM).
- **Cluster**: Core on CPU nodes; Workers on GPU nodes via secure transport.

## Key Capabilities (SRS Targets)

- Zero-copy tensor transport via Apache Arrow shared memory.
- DAG compilation with validation, type checking, and caching.
- Worker sandboxing with restricted syscalls and network isolation.
- Human approvals for sensitive or high-cost actions.
- Tool registry with dependency resolution and security scanning.
- Audit trails for runs, approvals, and artifacts.

## Governance and Security (Production HA)

Production HA stack is defined in SRS and designed around:
- **AuthN**: Keycloak (OIDC)
- **AuthZ**: SpiceDB (relationship-based access control)
- **Policy**: OPA (policy decision point for approvals and gating)
- **Secrets**: Vault (no secrets in env vars)

See `docs/specs/06_enterprise_infrastructure_srs.md` for full details.

## Configuration Modes

Three modes are defined and enforced at the configuration layer:
- `development_sandbox`
- `development_live`
- `production`

Only resource limits may differ; behavior matches production.

## Developer Quick Start (Local)

This project is in active development. Use the SRS documents as source of truth.

Basic local steps (subject to change):

```bash
# Build Rust core
cargo build --release

# Install worker dependencies
pip install -r worker/requirements.txt

# Run core (example)
./target/release/vortex
```

## Production HA Notes

- Use Vault for all secrets (no secrets in env vars).
- Enforce policy via OPA and permissions via SpiceDB.
- Use Keycloak for OIDC and centralized identity.
- Keep external ports in 11000-11999 (Vortex Port Authority).
